# 展開キャッシュと RAM 層

内側アーカイブ(アーカイブの中のアーカイブ)の巻を開いたときだけ、内側アーカイブを丸ごと `data_dir/cache/` に取り出す。
入口は `spinebox/cache.py:45 ExtractionCache`、使う側は `spinebox/library.py:349 _expand`(入れ子の各段を再帰で開く)。

## 内容

- **置くのは内側アーカイブだけ。** 画像フォルダとアーカイブ内フォルダの巻は、ページを毎回元から読む(メモリに 1 ページずつ)
- **名前はキーの sha256。** キーは外側の絶対パス・サイズ・mtime・内側エントリ名・エントリ番号。外側が変われば別キーになり、
  古い方は LRU で自然に消える。元の階層・名前は再現しない。入れ子は親のキーを混ぜて段ごとに別のキーにする
  (7z → rar → rar → zip なら 3 ファイル。巻を開いている間はすべて使用中で消えない)
- **容量上限(`cache_limit_bytes`、既定 2 GiB)を超えたら、最後に使ったのが古いものから消す。** 1 つで上限を超えるものは
  置かずに 422 で断る(置いた瞬間に自分を消すことになるため)
- **使用中(pin)のファイルは消さない。** 巻を開いている間に別の巻を開いても、読んでいる最中のファイルは残る
- **スキャンでは使わない。** スキャンは目次だけ読む(GOAL.md フェーズ 1 の完了条件)。取り出すのは `GET /api/volumes/{id}` などで巻を開いたときと、重複候補のための指紋を作る明示操作(`POST /api/duplicates/scan`。[[duplicate-detection]])だけ
- 消えてもよいもの。消えていたら次に開くとき作り直す。書きかけ(`.tmp-*`)は起動時に消す
- **作らずに使う入口 `ExtractionCache.use_existing()`(#75)。** 取り出し済みなら `use()` と同じく使用中にして渡し、無ければ `NotCached`。
  `Library.open(extract=False)` がこれを使い、一覧の表紙が「取り出し済みの内側 zip の巻」だけを読む([[cover-thumbnails]])。
  表紙の置き場(`data_dir/thumbs/`)も同じ `ExtractionCache` を別の上限で使っている
- **RAM 層(`spinebox/cache.py MemoryCache`、上限 `memory_cache_limit_bytes`、既定 256 MiB、0 で無効)には 7z / rar のページと目次だけを置く。**
  使う側は `spinebox/library.py Library._read_page()` / `Library._list()`。ページのキーは「そのページを持つ書庫のキー(外側なら上の
  外側のキー、内側なら展開キャッシュのキー)+ エントリ番号 + 名前」、目次のキーも書庫のキーから作るので、元が変われば別キーになる。
  合計が上限を超えたら最後に使ったのが古いものから消し、1 つで上限を超えるものは置かない。再起動で消える
- **7z / rar のページは、要求されたページから先を 1 回の 7-Zip 起動でまとめて取り出して RAM に置く**
  (`spinebox/archive/sevenzip.py SevenZipReader.read_entries()`。出力を目次のサイズで切り分け、CRC で照合する。[[archive-reading]])。
  まとめる枚数は前回の取り出しの続きを読むたびに 1 → 2 → 4 … 64 枚と倍にし、続きでなければ 1 枚に戻す(`_ArchiveState`)。
  バイト数は 128 MiB と RAM 層の上限の 1/4 の小さい方まで。同じ書庫の取り出しは直列化し(フロントは前後を並行で先読みする)、
  後から来た要求は先の取り出しが置いたものを使う。まとめ取り出しが失敗したら、要求されたページだけを 1 枚で読み直す
- **分解で作った子の巻も同じキーで取り出す**(`spinebox/library.py:303 _extract`)。親を開いた後に子を開いても取り出し直さない。
  子は親の内側アーカイブから自分の段までだけを取り出すので、v01 を読むのに v02・v03 の zip は取り出さない([[volume-split]])

## なぜこうなっているか

- アーカイブ内の仮想パスは 257〜259 文字に達する(GOAL.md「試作で確かめた前提」)。元の階層を再現すると Windows のパス長制限と
  `..` 等の危険な名前の両方を踏む。ハッシュ名ならどちらも起きない
- 内側アーカイブは丸ごと取り出さないと中の目次が読めない(zip の目次は末尾にあり、外側からのストリームでは読めない)。
  ページ単位で取り出すより、1 回取り出して以後はキャッシュから読む方が速い。外側がソリッド 7z だと、1 エントリの取り出しは
  その塊の先頭から展開するので特に差が出る(実データで 130 MB の zip が約 2 秒、キャッシュ済みなら 0)
- **RAM 層を 7z / rar に絞ったのは計測の結果**(#54、`scripts/bench_reading.py`。合成データ 60 ページ・1 ページ 400 KiB、開発機の Linux と 7-Zip 23.01、
  API 越しに 3 回の中央値)。ページを RAM に置いても zip / cbz・内側 zip は 1 ページ約 5 ms のまま変わらず(OS のファイルキャッシュが
  効いている)、効いたのは 7-Zip の起動と、ソリッド 7z の「1 エントリごとに塊の先頭から展開し直す」の 2 つだった:

  | 巻 | RAM 層 | 1 ページ目 | ページ送り(1 巻通読の平均 / 最大) | 同じページ | 開き直す |
  | --- | --- | ---: | ---: | ---: | ---: |
  | ソリッド 7z | なし | 46 ms | 892 / 1699 ms | 42 ms | 10 ms |
  | ソリッド 7z | 256 MiB | 36 ms | 60 / 1711 ms | 4 ms | 4 ms |
  | 7z の中の rar | なし | 24 ms | 23 / 27 ms | 24 ms | 17 ms |
  | 7z の中の rar | 256 MiB | 12 ms | 7 / 50 ms | 5 ms | 5 ms |
  | cbz | なし / 256 MiB | 5 / 7 ms | 5 / 5 ms | 5 / 5 ms | 5 / 5 ms |

  ソリッド 7z を RAM 層なしで読むと、後ろのページほど遅い(1 ページごとに塊の先頭から展開し直す)。RAM 層ありでも、まとめ取り出しが
  走る数ページ(1 巻で 6 回ほど)では同じく先頭から展開し直すので、最大の待ちは変わらない(合成データは LZMA の展開が実データより遅い)。
  最初から 16 枚まとめると 1 ページ目が 43 ms → 470 ms に悪化したので、1 枚から倍にしていく形にした。
  上限の枚数は 16 / 32 / 64 で比べ、120 ページ通読の平均が 144 / 86 / 70 ms だったので 64 にした
- 7z / rar の目次(`7z l`)も RAM 層に持ち越す。ページの要求ごとに巻を開き直す作り(`GET .../pages/{i}` は毎回 `Library.open()`)なので、
  持ち越さないと 1 ページごとに外側・内側の `7z l` が走る(上の「開き直す」の差)
- 最終使用順はプロセス内のカウンタで持つ。ファイルの mtime だけだと、同じ時刻分解能内の連続アクセスで順序が決まらない。
  使うたびに mtime も触るので、再起動後は mtime の順で復元する

## 検討して採らなかった選択肢

| 案 | 却下した理由 |
| --- | --- |
| ページ画像もディスクの展開キャッシュに置く | 外側アーカイブ・フォルダから直接読めるので不要。ブラウザ側は `ETag` / `Cache-Control` で再取得を減らす。7z / rar のページは RAM 層に置く(上) |
| スキャン時に内側アーカイブを取り出してページ数を数える | 完了条件「スキャンでは内側のアーカイブを 1 つも取り出さない」に反する。蔵書全体を一度に展開することになる |
| 一時ディレクトリ(OS の temp)に置く | 容量の管理ができず、再起動で消える。設定の `data_dir` 配下に置く |
| zip / cbz のページも RAM 層に置く | 計測で差が出なかった(1 ページ約 5 ms のまま)。RAM を 7z / rar のページに回す |
| 内側の zip を展開キャッシュではなく RAM(`BytesIO`)に置く | 計測で差が出なかった(24 MiB の内側 zip で、取り出し 18.8 → 19.0 ms、開いて 1 ページ 0.31 → 0.51 ms)。ディスクの方は再起動後も残る |
| 7z / rar の巻を開いたら全ページを 1 回で取り出す | 開いて最初のページが出るまでが巻全体の展開時間になる(上の 16 枚でも 470 ms)。倍々に増やす形にした |
| 1 つの 7-Zip を起動したまま、裏で巻の最後まで流し続ける | まとめ取り出しのたびに塊の先頭から展開し直す待ちは消えるが、プロセスの寿命・中断・メモリの管理が要る。今回は入れていない。実データの計測で待ちが目立てば検討する |

## 実データでの計測(`_参考/サンプル本`、開発機 Windows・7-Zip 26.02)

`scripts/bench_reading.py --root _参考/サンプル本 --children`(API 越し、3 回の中央値、ページ送りは 30 ページ。RAM 層 なし → 256 MiB。2 GiB も同じ傾向)。
**実データで効いているのは目次の持ち越しで、ページ画像を RAM に置く分は出番が無かった**: サンプルの `v01-03.rar` は中身が zip の入れ子
(7z → rar → zip)で、ページを読むのは zip(`batch_reads` = False)だから。

| 巻 | 1 ページ目 | ページ送り(平均 / 最大) | 同じページ | 開き直す |
| --- | ---: | ---: | ---: | ---: |
| 普通の zip(190 ページ) | 34.8 → 33.5 ms | 37.1 / 53 → 35.5 / 51 ms | 38.7 → 33.1 ms | 31.7 → 31.0 ms |
| 7z → rar → zip のまとめ(472 ページ) | 112.8 → 22.4 ms | 110.6 / 123 → 20.8 / 31 ms | 111.4 → 34.1 ms | 111.8 → 20.2 ms |
| 同・子の巻 v01(157 ページ) | 100.8 → 12.2 ms | 142.1 / 771 → 10.0 / 12 ms | 108.9 → 12.4 ms | 104.2 → 9.3 ms |
| 同・子の巻 v02 / v03 | 117.8 → 11.1 / 70.3 → 8.7 ms | 104.0 → 10.9 / 69.8 → 9.4 ms | 101.7 → 11.4 / 69.3 → 8.9 ms | 98.7 → 8.8 / 69.8 → 8.9 ms |
| 7z → zip(v04、159 ページ) | 425.6 → 9.8 ms | 45.5 / 65 → 9.0 / 10 ms | 41.8 → 9.7 ms | 39.6 → 9.3 ms |

- 普通の zip は変わらない(RAM 層に置いていない)。7z / rar が外側に付くと、ページの要求ごとの開き直しで `7z l` が走っていたのが
  1 回で済む。初回オープン(内側の取り出し。7z → zip で約 1.8 秒)は RAM 層とは無関係で変わらない
- サンプルに無い「画像を直接持つソリッド 7z」は、サンプルの JPEG(v04.zip の 159 ページ、126 MB)から作った ソリッド 7z で測った
  (ページ送り 平均 573 → 39 ms、同じページ 71 → 5.7 ms、最大の待ち 約 1.2 秒は変わらず)。rar は 7-Zip で作れないので合成の手組みのみ
- 上限の確認: 合成データ(7z / rar 入りの 5 巻 × 120 ページ、1 ページ 400 KiB)を全ページ往復で読み、上限 16 MiB で最大 15.7 MiB、
  64 MiB で最大 63.8 MiB(超えない)。回帰テストは `tests/test_memory_cache.py`

## 覆すとしたら

- 合成データの 7z は LZMA の展開が遅め(1 巻 24 MiB の内側 rar の取り出しに約 1.7 秒。実データは 130 MB で約 2 秒)なので、
  待ちの絶対値は実データの方が小さい見込み。画像を直接持つ 7z / rar の実蔵書(サーバー機)で効果を確かめるときも同じスクリプトを使う

- フェーズ 2 で 1 巻 = 1 CBZ に平坦化が進めば、内側アーカイブの巻自体が減り、キャッシュの役割は小さくなる
- 7z / rar の取り出しは 7-Zip CLI の `-so`(標準出力)を `ExtractionCache.use()` が渡すファイルに流している。CLI に元の名前・階層で
  展開させていないので、ここの前提(ハッシュ名・上限・使用中は消さない)はそのまま成り立つ
