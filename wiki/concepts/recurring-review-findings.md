# 繰り返し指摘される誤り

レビュー(agy レビュー)で**妥当と判定して直した指摘**を、誤りの種類ごとにまとめた台帳。
個々の指摘は PR コメントに残るが、そこは merge hook と経緯を追う人しか読まない。
ここに集めておかないと、次の実装者は同じ種類の誤りを別の場所でまた作る。

**実例の出どころ:** 導入時点で載っている実例の PR 番号は、導入元テンプレート
([kant0123/ai-coding-template](https://github.com/kant0123/ai-coding-template))と、その導入先のものである。
誤りの種類は SpineBox にもそのまま当てはまるので残している。SpineBox で足す実例は SpineBox の PR 番号で書く。

**読むタイミング:** 着手時(`worktree-start` 手順 1)と push 前(`pr-finish` の前提の確認)。
push 前は、自分の差分が下の各種類に当てはまらないかを 1 つずつ確かめる。

**書くタイミング:** 差し戻しの指摘を妥当と判定して直したとき(`agy-review` 手順 3)。
既存の種類に当てはまれば実例を 1 行足し、無ければ種類を足す。
**未確認と判定した指摘は載せない。** 成立を確かめていないものを実装側の誤りとして記録すると、
推測が「繰り返される誤り」として次の実装者に読まれる。

## 書き方

- **単位は種類であって個々の指摘ではない。** 「`foo()` の空文字列を見ていなかった」ではなく
  「外部コマンドの出力が空・想定外の形のときを考えていない」と書く。事象ごとに書くと、
  次に別の関数で出る同じ誤りに当てはめられない。
- 各種類には「push 前に確かめること」を書く。自分の差分に対して答えられる問いの形にする。
- 実例は `PR 番号 — 場所 — 一行` で。修正コミットや PR を辿れれば詳細はそこにある(本文を貼らない)。
- 種類の数は増やしすぎない。似た種類が並んだら統合する。

誤検知(`false-positive`)と見逃し(`false-negative`)はここではなく上流の Issue に送る
(`review/README.md` の「記録の置き場所」)。未確認はこのリポジトリの Issue に起票する(上流には送らない。`agy-review` 手順 4)。ここはレビュー役ではなく**実装側の誤り**の記録。

> 初期の実例はこのテンプレート自身(`review/agy_review.py`)の開発で出たもの。
> 他プロジェクトに導入したら実例は消してよいが、種類はそのまま当てはまることが多い。

## 種類

### 外部コマンド・外部出力の異常系を考えていない

外部コマンド(`gh` / `git` / LLM CLI)やファイルシステムが返すものを、正常系の形のまま信じている。
空出力・非ゼロ終了・前置き付きの出力・エスケープされた値・OS で不正な文字を含む値で壊れる。

push 前に確かめること:

- 外部コマンドが失敗したとき・出力が空のとき、処理は止まるか。黙って成功扱いに倒れていないか
- 出力を解釈する正規表現・パーサは、引用符・空白・非 ASCII・前置き・CRLF の付いた値でも合うか
- 外部から来たパスを `resolve()` / `open()` する前に、不正な値で例外が出たときの扱いがあるか
- 同じ記録(PR コメント等)が何度も書かれうるとき、どれを正とするか(最新か・全部か)を決めているか
- 標準出力を解釈するとき、標準エラーを混ぜていないか(警告 1 行で値を読み違える)
- Windows PowerShell 5.1 のスクリプトで、`$ErrorActionPreference = "Stop"` のまま外部コマンドの stderr を受けていないか(警告・進み具合の 1 行で例外になる。成否は終了コードで見る)
- 同じ値を 2 か所で作って比べるとき、形(短縮 SHA の長さなど)がそろっているか

実例:

- PR #8 — `review/agy_review.py ci_state()` — `gh pr checks` が失敗して出力が空のときに緑と判定していた
- PR #8 — `review/agy_review.py` JSON 抽出 — LLM 出力に前置きがあると JSON を取り出せない
- PR #20 — `review/agy_review.py` 差分パスの抽出 — 空白・非 ASCII を含むパスは `git diff` が引用符で囲むため正規表現に合わない
- PR #20 — `review/agy_review.py` パスの解決 — Windows で不正な文字を含むパスで `OSError`
- PR #33 — `review/agy_review.py has_unverified_critical()` — 評価の理由文に「未確認」があるだけで判定語と取り違えていた
- PR #33 — `review/agy_review.py has_unverified_critical()` — 過去の評価も見ていて、記録し直しても差し止めが解けなかった
- PR #97 — `deploy/update_spinebox.ps1 Get-HealthUrl` — `--print-bind` の出力を `2>&1` で読み、設定の警告(使われなくなったキー)が stderr に出ると host を読み違えた。直したら今度は Windows PowerShell 5.1 が stderr を例外にして止まった(警告の出る偽の spinebox で再現・修正)
- PR #97 — `deploy/update_spinebox.ps1` 起動前のコミット取得 — `git` が失敗すると同じく例外で止まり、「途中で失敗しても起動し直す」に届かなかった(git リポジトリでない場所で再現)。比べる短縮 SHA もアプリ(7 文字固定)と git の既定(環境で長くなる)で長さがずれていた。さらに `/healthz` が `commit: null`(git が見えない環境)を返すと照合の前に null のメソッドを呼んで例外になり、正常起動でもタイムアウトしていた(偽の /healthz で再現・修正)
- 導入先 MeltKelp PR #16 — `.claude/hooks/command_match.mjs` ヒアドキュメントの終端行 — CRLF の入力だと終端行が `EOF\r` になって区切り語と一致せず、後ろのマージのコマンドまで本文として読み飛ばして素通ししていた(agy レビューで発覚。`\r` を除いて再現・修正)
- PR #128 — `scripts/worktree-cleanup.ps1` — `.gitignore` 外の未追跡ファイルがある worktree に対して `--force` 無しで `git worktree remove` を呼び、失敗して `.git` ファイルが残ったままの状態で先に `git worktree prune` を走らせてから作業ディレクトリだけ `Remove-Item` していたため、`.git/worktrees/<id>` が残って後続のブランチ削除が失敗した(agy レビューの WARNING。`-RemoveDirs` 指定時は `--force` を付け、残骸削除の後に `git worktree prune` を走らせる順序に修正。また PR マージ直後のローカル `main` はリモートのマージコミットを未取得で `git push origin --delete` により追跡ブランチも消えているため、後始末のローカルブランチ削除は `-d` ではなく `git branch -D` にした)

### 新しく足した分岐・関数にテストが無い

既存の純粋関数のテストはあるが、今回足した分岐(再試行・エラー経路・オプションの付与)には無い。
レビューで指摘されてから足すことが繰り返されている。

push 前に確かめること:

- 差分で足した `if` / `except` / 引数の付け足しのそれぞれに、そこを通るテストがあるか
- 外部プロセスを呼ぶ関数は、呼び出しをモックして「何を渡したか」を assert しているか

実例:

- PR #8 — `review/agy_review.py` — `cmd_review` / `cmd_triage` / `cmd_check` / `call_agy` / `ci_state` にテストが無かった
- PR #23 — `review/agy_review.py call_agy()` — 再試行時の `--conversation` 付与にテストが無かった
- PR #61 — `spinebox/app.py background_metadata()` — 設定で有効にしたときに常駐する裏のスレッドにテストが無かった(既存の裏の解析は `tests/test_analysis.py` に有る。足したら同じ形で足す)
- PR #97 — `deploy/update_spinebox.ps1` — 「途中の手順が失敗しても起動し直す」「止められなければ何もしない」の分岐にテストが無かった(止める・起動するを `-TaskRunner` で差し替えられるようにしてテストを足した)
- PR #61 — `spinebox/app.py _run_metadata_fetch()` — 進み具合(`done`)を各作品の開始時にしか更新せず、全件完了後も `done < total` のままだった(完了時の状態を確かめるテストが無かった)
- PR #128 — `tests/test_deploy_scripts.py` — `worktree-cleanup.ps1` の削除テストで `.gitignore` 対象のファイルだけ置いて `.gitignore` 外の未追跡ファイルを置かず、削除後に `.git/worktrees/<id>` が消えてコミットを持つ作業ブランチに対する `git branch -D` が通ることも assert していなかった(agy レビューの WARNING)

### ルールを足したのに、同じ流れを書いた他の箇所と食い違う

ルールを 1 か所(スキルの表・CLAUDE.md)に足し、同じ流れを別に書いている箇所
(手順の見出しと結び・フローチャート・他スキルのテンプレート・hook の判定)を直していない。
読む場所によって逆の指示が出る。機械で見張れるルールを文書にしか書かないのも同じ誤り。

push 前に確かめること:

- 足したルールのキーワードで `grep` して、同じ流れを書いた箇所(見出し・図・テンプレート)がすべて整合しているか
- そのルールは hook / CI で判定できる形か。できるなら判定を足したか

実例:

- PR #33 — `.agent/skills/agy-review/SKILL.md` 手順 4 — 「CRITICAL が未確認ならマージしない」を足したが、手順 4 の見出しと結びは未確認でも無条件にマージさせていた
- PR #33 — `review/agy_review.py check_merge()` — 同じルールを hook が判定していなかった
- PR #33 — `.agent/skills/pr-finish/SKILL.md` — PR 本文テンプレートと手順 4 の振り分けに「未確認」が無かった
- PR #33 — `.agent/skills/agy-review/SKILL.md` フローチャート — 未確認の CRITICAL もマージに至る経路として描いていた(この種類を台帳に足した PR 自身で再発)
- PR #35 — `wiki/concepts/recurring-review-findings.md` — 「未確認は台帳に載せない」を足したが、同じページの送り先の説明に未確認の行き先が無かった
- PR #40 — `spinebox/duplicates.py candidate_counts()` — 画面の API は「一覧に見えている巻どうしの組」だけを出すのに、一覧の印の数は見える条件を掛けず、片方が missing になった候補を数えて「開いても何も出ない印」が残った(missing にして再現)
- PR #47 — `.agent/rules/git-workflow.md` / `knowledge-wiki.md` — `CLAUDE.md` の写しとして足したが、agy レビュー・両論併記・lint はコミット後の不変条件が抜けていた(外部レビューで発覚)
- PR #61 — `spinebox/app.py decide_work_proposal()` — 手動の統合には連携の反映(`_sync_works`)を足したのに、同じ統合を行う提案の承認には足さず、統合で増えた巻に書誌が入らなかった
- PR #61 — `spinebox/linking.py choose()` / `reset_link()` — API 契約と mock は未知の取得元を 404 としたが、実装は 409 を返した(契約・mock・実装の突き合わせ漏れ)
- PR #61 — `spinebox/linking.py reset_link()` / `_store()` — 連携を決める通常の経路(`fetch_work`)には「種別が未決なら保留」「作品の種別と食い違う候補は除く」があるのに、手動の選択を解除する経路と、自動連携を保つ近道は通らず、規則を飛ばして連携した(同じ判定を `decide()` へ集める。近道は判定の前提を満たすときだけ)
- PR #118 — `.agent/skills/dads-ui/SKILL.md`「設計思想」 — 角丸・字を「ローカルに決めてよい」と書きながら、同じページの表と手順 3 では「DADS の値をそのまま使う」としており、逆の指示になっていた(agy レビューの WARNING。同じ内容の `.claude/skills/` の写しも)
- PR #127 — `frontend/src/organize/OrganizeFiles.tsx` / `Inbox.tsx` — DADS のフォーム部品でサポートテキストを `<label>` と `<input>` の間に置くと定めたのに、`#organize-path`・`#organize-folder-template`・`Inbox` の作品名では `<input>` の下に置き、`Inbox` では空白を含みうる `rel_path` を HTML の `id` / `aria-describedby` に埋め込んでいた(agy レビューの WARNING。`source_id` に変え、`compareDocumentPosition` で `<input>` より前にあることを確かめるテストを足した)
- PR #135 — `spinebox/organize/organizer.py _range_cbz_target_problem()` / `_check_range_cbz_item()` — 改名・移動の「出力先に同じ `sources` 行があれば衝突」を CBZ 化にもそのまま使ったが、CBZ 化は実行時に `_upsert_source` で missing の行を再利用する。実行 → 元に戻した後の再計画が常に「この場所にあったファイルの記録が残っています」で衝突になった(undo 後の再計画・再実行のテストで再現し、CBZ 化からは `sources` の存在チェックを外した)

### 同じ規則で判定すべき対象を、種類ごとに先に別々に判定している

「同じ名前の巻はファイル数の多い方を残す」のように、対象全体を比べて決める規則を、対象の種類(単巻・CBZ 化する元)ごとに先に判定してから足し合わせる。
先に判定した側が結果(衝突など)を確定するので、あとからの全体の判定はそれらを対象から外し、種類をまたいだ比較が抜ける。

push 前に確かめること:

- 規則が比べる対象を全部列挙し、判定が 1 回の全体の比較になっているか(部分ごとの判定を先に走らせていないか)
- 種類が違う対象が同じ結果(同じ出力名)になるテストがあるか。片方の種類だけの重複を確かめたテストは、この漏れを通す

実例:

- PR #144 — `spinebox/organize/organizer.py _plan_range_cbz()` — 単巻の振り分け(`_classify_renames`)が単巻どうしの重複だけで衝突・譲りを決め、同じ名前の CBZ 化の元と比べなかった。単巻が同数で衝突していると、ファイル数の少ない元が `cbz` のまま確定した(単巻 5・5 と画像フォルダ 2 で再現し、`dedupe=False` で全体の判定へ寄せた)

### 外部ツールの設定形式を一次資料で確かめずに書く

他ツール(Antigravity・GitHub Actions 等)の設定ファイルの形を、要約・記憶・似たツールからの類推で書く。
値が配列かオブジェクトか、作業ディレクトリはどこか、といった細部が違っていても読む側は気付けず、
テンプレートどおりに作った設定が黙って効かない。

push 前に確かめること:

- 設定例の各キーと値の型(配列か・オブジェクトか)を、公式ドキュメントの例と 1 つずつ突き合わせたか
- パスを含む設定は、どこを起点に解決されるか(リポジトリ直下か・設定ファイルの場所か)を確かめたか
- 組み込みの既定(シェル・ランナーの設定)を自前の指定に置き換えるなら、既定が暗黙に足していたもの
  (エラーで止める・終了コードを伝える)を一次資料で確かめ、自分で足したか

実例:

- PR #47 — `.agent/skills/agent-config-manager/SKILL.md` Hook テンプレート — `PreToolUse` を配列ではなくオブジェクトで書き、コマンドのパスも作業ディレクトリ(`hooks.json` の場所)を考えていなかった
- PR #48 — `.github/workflows-optional/deploy.yml` — シェル行を自前指定にして、組み込みの `shell: powershell` / `pwsh` が前に足す `$ErrorActionPreference = 'stop'` を失い、デプロイスクリプトが無くても exit 0 で緑になっていた(導入先 MeltKelp の PR #11 の agy レビューで発覚。手元の Windows PowerShell 5.1 で再現)

### 主目的のページ以外に触った Wiki の付随更新を漏らす

新しいページを書くことに気を取られ、リンクを張るためだけに触った既存ページの `updated`、
`log.md` の「更新:」行を漏らす。`wiki-lint` はテンプレートのプレースホルダーのような
一部のケースを注意止まりにするので、lint が通っても漏れは残る。

push 前に確かめること:

- `git diff --stat origin/main -- wiki/` に出る各ページの `updated` を今日にしたか
- 同じ一覧のページが、`log.md` のエントリの「更新:」「新規:」にすべて載っているか

実例:

- PR #40 — `wiki/log.md` — 取り込みで触った `wiki/components/organize.md` と、`archive-reading` の相互参照を「更新:」に載せていなかった
- PR #34 — `wiki/overview.md` — リンクを足したが `updated` をプレースホルダーのまま残し、log の「更新:」にも載せなかった
- PR #59 — `wiki/log.md` / 各ページの `updated` — クラウドで書いたエントリの日付が UTC の `2026-11-01` で、main の JST の `2026-11-02` より前に巻き戻っていた(agy の NITPICK。`git log` の日付と、直前のエントリの日付で確かめて直した)
- PR #91 — `wiki/components/backend.md` API 契約表 — 新しいエンドポイント(`range-plan`・`range/options`・`range/example`・`range/folders`)と `GET /api/organize` の `kind` の値(`range`)を表に足していなかった。行番号の直しだけでページに触れていたので「更新済み」に見えていた

### 「手動の決定を守る」判定が、手動になりうる項目の全部を見ていない

「手で編集したものは外部ソース・自動処理で上書きしない」を、手動フラグを持つ項目の一部(作品名・巻の割り当て)でだけ判定している。
後から足した項目(著者)や、自動処理が結果を返す先(統合で吸収された作品)で、手動の値が黙って落ちる・操作が失敗に見える。

push 前に確かめること:

- 手動フラグを持つ列・行(`manual`)を全部列挙し、「手動が絡むか」の判定がその全部を見ているか(1 項目ずつ書き足した判定は漏れる)
- 2 つの値を寄せる処理(統合・上書き)で、手動の値が名前から読んだ値に負けて見えなくなる分岐が無いか
- 操作の直後に自動処理(再計算・自動統合)が走るとき、返す id の対象が操作で消える(吸収・削除)ことがないか。あるなら吸収先を返し、画面もそちらへ移るか

実例:

- PR #47 — `spinebox/works.py _manual_involved()`(旧 `_Work.manual_involved`) — 手動の著者を「手動が絡む」に数えず、確信度の高い自動統合の対象にしていた(手動の著者だけを入れた作品が重複証拠で自動統合されることを再現)
- PR #47 — `spinebox/works.py merge_works()` — 吸収される作品の手動の著者を、残る作品のファイル名由来の著者が隠していた(手動統合で再現)
- PR #47 — `spinebox/app.py add_work_alias()` — 別名の一致で自動統合され操作した作品が吸収されると、吸収された id で詳細を引いて 404 を返していた(ローマ字の作品へ日本語名の別名を足して再現)
- PR #61 — `spinebox/works.py _manual_involved()` — 利用者が選んだ公開 DB の連携(`work_links.manual`)を「手動が絡む」に数えず、強い証拠があれば自動統合で吸収されうる状態だった(新しい手動の列を足したのに判定を足していなかった)
- PR #61 — `spinebox/app.py reset_work_field()` / `frontend/src/works/WorkPage.tsx apply()` — 手動の項目を自動に戻すと止まっていた自動統合が成り立って操作した作品が吸収されうるのに、吸収された id で詳細を引いて 404 にした。画面も、吸収先の詳細が返ってもページの URL を旧 id のままにしていた(別名の追加では対処済みだった。作品を返すエンドポイントと画面の更新口を全部見る)

### 導出した行を、元(連携・設定)が消えても残す

「元から導出して入れる」処理が、入れる側だけを書いて、元が外れたとき(連携の解除・候補の変更・再取得で消えた候補)に入れた行を消す側を書いていない。
項目や巻の書誌では戻すのに、同じ導出で入れた別の表(別名)だけ残り、誤った手がかりが名寄せや統合に使われ続ける。

push 前に確かめること:

- 導出で書く表を全部列挙し、元が無くなったときにそれぞれが消える(または元の値へ戻る)か。表ごとに「入れる」と「外す」が対になっているか
- 外す処理は手動の行と、利用者が外した行(`dismissed_at`)を巻き込んでいないか
- 「連携を外した後」の状態を確かめるテストがあるか(入れる方のテストだけだと漏れる)

実例:

- PR #61 — `spinebox/linking.py _apply_aliases()` — 連携を外しても公開 DB 由来の別名が残り、誤った別名が後の名寄せの手がかりになりえた(項目と巻の書誌は外せていたが別名だけ漏れた)

### 再試行・再実行で前回の成果物を上書きする

同じ処理を 2 回目に走らせたとき、1 回目の出力やログを同じパスに書いて消している。
失敗の調査に要る記録が、再試行が走った瞬間に失われる。

push 前に確かめること:

- 再試行・ループの中でファイルに書くなら、2 回目は追記か別名になっているか

実例:

- PR #23 — `review/agy_review.py` — 再試行で `agy_raw_output.txt` を上書きしていた

### 件数が増える処理で、1 件ごとに全体を引き直している

「未処理を 1 件取って処理し、また未処理の一覧を引く」のように、ループの中で全件の SELECT や全件の `stat()` を繰り返す。
数件では気づかず、蔵書が増えると巻数の 2 乗で効く。

push 前に確かめること:

- ループの中で、全件を引く SQL・全件を対象にするファイルシステム操作を呼んでいないか。引き直しが要るのは「一巡して新しい対象が現れたとき」だけか
- 呼び出し回数をテストで数えたか(`pending()` の呼び出しを数えて件数に比例しないことを確かめるなど)
- 蔵書全体の巻をまとめて渡される関数が、巻ごとに SELECT を発行していないか(巻の行・書誌は IN で 500 件ずつまとめて引く。作品のように重複する対象は 1 回ずつ)。`set_trace_callback` で文の数が巻の数に比例しないことを確かめたか

実例:

- PR #40 — `spinebox/duplicates.py DuplicateScanner.run()` — 指紋を 1 巻作るたびに `pending()`(全巻の SELECT と作成済みの巻すべての `stat()`)を呼んでいた。`pending` の呼び出し回数を数えて再現し、1 巡ごとに直した
- PR #91 — `spinebox/organize/organizer.py name_values()` — 範囲指定が蔵書ルート全体の巻を渡すのに、巻ごとに 3 回 SELECT していた(20000 巻で 1.1 秒。10 万巻規模で効く)。文の数を数えるテストを足して `IN` でまとめて引くようにした
- PR #94 — `spinebox/stats.py collect()` — 全作品の表紙の有無を見るのに、作品ごとに `is_built()`(巻の行を 1 件 SELECT)を呼んでいた。`get_volume_rows()` で 500 件ずつ IN でまとめて引く `Thumbnails.are_built()` にし、文の数が巻の数に比例しないことを `set_trace_callback` で確かめるテストを足した
- PR #135 — `spinebox/organize/organizer.py _plan_range_cbz()` — `include_cbz` の計画で 1 巻 = 1 CBZ の巻ごとに `_classify_renames([r], ...)` を呼び、その中の `sources`・画像フォルダの SELECT が巻数ぶん出た。1 回の `_classify_renames` にまとめ、`folder_sources` / `source_paths` のキャッシュを渡すようにした。計画の SELECT 数が巻数に比例しないことを `set_trace_callback` で確かめるテストを足した

### 共有すべき状態を、呼び出しごとに作るインスタンスに持たせている

レート制限の関門・接続プール・キャッシュのように、**リクエストをまたいで持ち越さないと意味がない状態**を、
リクエストごとに作るオブジェクトの中に持たせる。使うたびにリセットされて制限が効かず、逆に共有を渡すと
`close()` が呼び出し側のものまで閉じる(所有権が曖昧)。ドキュメントの使用例どおりに呼ぶと起きるので、テストでは
明示的に 1 つを渡していて気づけない。

push 前に確かめること:

- ドキュメント(wiki の使用例)どおりに「リクエストごとにインスタンスを作る」と、制限・接続は共有されるか。デフォルトの経路で確かめたか
- 外から渡されたオブジェクトを `close()` していないか。自分で作ったものだけを閉じているか

実例:

- PR #46 — `spinebox/metadata/service.py MetadataService` — 取得元ごとのレート制限の関門を持つ `HttpFetcher` を呼び出しごとに作り、`close()` は渡された共有 fetcher まで閉じていた。2 つのサービスの fetcher が別物になることと、渡した fetcher が閉じることをテストで再現して直した(プロセス共有の `shared_fetcher`、所有している fetcher だけを閉じる)

### 正規化の前提と、その前段の判定が別々の文字集合を見ている

文字列を種類(ローマ字 / 日本語)で振り分けてから正規化する処理で、振り分けの判定(`ord(c) < 128`)と、
振り分け先の正規化が扱う文字(マクロン付きラテン文字)が食い違う。正規化は対応しているのに、そこへ届かず日本語側に回り、
同じ名前が一致しない・比べられないはずの組が減点される。

push 前に確かめること:

- 振り分ける関数と、振り分け先が扱う文字集合は一致しているか。境界の文字(マクロン・全角英数・記号だけの文字列)を入力にしたテストがあるか

実例:

- PR #46 — `spinebox/metadata/match.py` ローマ字判定 — `Tōkyō` を非 ASCII として日本語側の正規化に回し `Tokyo` と一致せず、著者もローマ字名が日本語名と「同じ表記体系」とみなされて減点されていた。両方を再現して `is_romaji_word` に揃えた


### 利用者が打ったパスの綴りを、そのままデータベースの値と比べる

利用者が入力したパス(範囲・フォルダ名など)を、検証だけファイルシステムに任せ、比較や出力にはそのまま使っている。
Windows では大文字小文字が違っても同じフォルダを指す(存在確認は通る)が、DB の相対パスとの前方一致は文字列比較なので外れ、
「巻がありません」になる。出力先のフォルダ名も打った綴りのまま作られる。

push 前に確かめること:

- 利用者が打ったパスを DB の値と文字列で比べる前に、ディスク上の綴りへ直しているか。大文字小文字を変えて打ったテストがあるか
- 大文字小文字を区別するファイルシステムでは別のフォルダを取り違えない(ぴったり同じ名前を先に採る)か

実例:

- PR #91 — `spinebox/organize/organizer.py range_path()` — 範囲のパスを `manga/SUB` と打つと `is_dir()` は通るのに `Manga/Sub/...` と前方一致せず、計画が空になった。区切りごとにディスク上の綴りへ直す `_disk_case()` を足した

### 既存のクラス・関数の役割を、コードを確かめずに文書に書く

差分の外にある既存の CSS クラス・関数・設定の意味を、名前や過去の不具合の記憶から推測して
スキル・Wiki・コメントに書く。実際の役割と逆だったり、一部の用途しか見ていなかったりして、
読んだ実装者が共通部品を避ける・壊す。

push 前に確かめること:

- 文書に書いた既存のクラス・関数・設定の役割を、定義箇所と利用箇所(2 か所以上)で確かめたか
- 「使わない」「禁止」と書く対象が、本当にその用途で使われていないか(grep で利用箇所を見たか)

実例:

- PR #111 — `.agent/skills/dads-ui/SKILL.md`「このリポジトリの罠」 — `.page` を「リーダーの紙面用なので新しい画面のコンテナに使わない」と書いたが、実際は `frontend/src/styles.css` で `.page` が画面共通の枠(`max-width: 1100px`)で、`Admin.tsx` / `FacetList.tsx` が使っている。#99 / #100 の修正はリーダー側の `pointer-events: none` を `.stage .page` に限定したものだった(agy レビューの WARNING で発覚)

### 既存のクラス名を確かめずに、同じ名前のスタイルを足す

新しい画面・部品に、既にあるのと同じ名前の CSS クラスを付けて `styles.css` の後ろに定義を足す。
後勝ちで既存の画面の余白・間隔・色が変わる。見た目の崩れは単体テストに出ないので、
レビューでしか見つからない。

push 前に確かめること:

- 新しく足すクラス名を `frontend/src/styles.css` 全体で検索し、既に定義があるなら
  スコープを付ける(`.title-modal .dup-list`)か別名にしたか
- 既存の画面でそのクラスを使っている箇所を grep で見たか

実例:

- PR #120 — `frontend/src/styles.css` タイトル一覧のモーダル — モーダルの一覧に `.dup-list` を足し、
  既存の重複候補画面(`frontend/src/duplicates/Duplicates.tsx`)の `.dup-list`(gap 14px・margin 12px 0 0)を
  後勝ちで上書きした。`.title-modal .dup-list` にスコープして修正

### 一度取り出した値を捨てて、元の文字列から作り直す

構造化した結果(名前・著者・根拠の組)を途中まで作っておきながら、下流へは文字列だけ渡し、
渡された側で同じ文字列を再パースする。パースは前置き・括弧・番号を落とすので、2 回目では
元の情報が戻らず、項目が黙って空になる。

push 前に確かめること:

- パース結果を下流の関数へ渡すとき、その型のまま渡しているか。文字列へ戻して再パースしていないか
- 再パースで落ちる項目(著者・根拠・出所)が、テストで確かめられているか。値だけでなく
  `parts` のような根拠も見ているか

実例:

- PR #159 — `spinebox/works.py own_name()` — `_trailing_series()` が `parse_work_name()` の結果から
  `title` だけを渡し、`own_name()` がそれを再パースしていたため、`[著者] 作品名 01` の著者が落ちて
  作品の著者が空になった(著者つきの名前で再現し、`WorkName` をそのまま渡すように修正)

### 条件式で変数の意味を取り違え、境界を確かめていない

位置(`m.start()`)と値(`start`)を同じ条件で混用する。負のインデックスや先頭付近の参照で例外・誤判定になる。

push 前に確かめること:

- 条件式の各変数が「位置」か「値」か。位置を境界に使うとき、参照する添字の範囲を確かめたか
- 文字列の先頭・末尾付近を参照するとき、負のインデックスや `IndexError` にならないか
- 境界の入力(先頭の番号・末尾の数字・小数点)のテストがあるか

実例:

- PR #172 — `spinebox/naming.py:86 _find_number()` — 小数点の巻の判定で、巻番号の値 `start` を添字の境界として使い、`4.1巻` を `1巻` と誤読し、先頭付近で負のインデックスを参照しうる状態だった(agy レビューの WARNING。`m.start() >= 2` に修正し、`4.1巻` のテストを足した)

### 共通の後処理を分岐の片側だけに置いている

`if` の片側でだけ行う処理を、両方の分岐に必要な共通の後処理なのに片側に置く。もう一方の分岐ではその処理が抜ける。

push 前に確かめること:

- `if` / `else` の両方に同じ後処理が必要か。必要なら分岐の外(後ろ)に置いたか
- 両方の分岐を通るテストがあるか。片側だけのテストは漏れを通す

実例:

- PR #172 — `spinebox/works.py:516 _assign_volumes()` — 番号付きの作品から系列名の作品へ付け替えるときの `_merge_links()` を、系列名の作品を新設する `if target is None:` の側にだけ置き、既存の系列名の作品へ付け替える `else` 側では連携が移らなかった(agy レビューの WARNING。分岐の外へ移し、2 巻目以降の連携を移すテストを足した)

### 解析規則を変えたのに、既存データを読み直す版を上げていない

`parse_number()` などの読み方を変えたとき、`SCAN_VERSION` を上げないと、同じサイズ・mtime のアーカイブは unchanged と判定され、既存 DB の番号が読み直されない。

push 前に確かめること:

- 名前・番号の読み方を変えたか。変えたなら `SCAN_VERSION` を上げたか
- 既存 DB を読み直すテスト、または版を上げたことのテストがあるか
- 名寄せで直る導出値と、スキャンでしか直らない値(`number_*`)を区別しているか

実例:

- PR #172 — `spinebox/scanner.py:44 SCAN_VERSION` — `parse_number()` に `卷` と小数点の巻の読み方を足したのに `SCAN_VERSION` を 2 のままにしていた(agy レビューの WARNING。3 に上げた)

### 変化が無ければ書かない処理で、条件の抜けにより毎回書く

「冪等で、変化が無ければ書かない」処理の更新条件に、対象の値が存在するかのガードを入れず、値が無い行にも毎回 UPDATE を発行する。`updated_at` が毎回変わり、契約と DB の書き込み量が破れる。

push 前に確かめること:

- 更新する条件は、対象の値が NULL の行を除外しているか
- 何も変えない再実行で、行の `updated_at` が変わらないテストがあるか
- ループ内で、条件が常に真になる行がないか

実例:

- PR #172 — `spinebox/works.py:504 _apply_trailing_numbers()` — 小数点の巻の番号を消す条件に `parse_number() is None` だけを入れ、`number_kind is None` の巻も毎回 UPDATE して `updated_at` を書き換えていた(agy レビューの WARNING。`number_kind is not None` のガードを足し、番号なしの巻の行が変わらないテストを足した)
