# 繰り返し指摘される誤り

レビュー(agy レビュー)で**妥当と判定して直した指摘**を、誤りの種類ごとにまとめた台帳。
個々の指摘は PR コメントに残るが、そこは merge hook と経緯を追う人しか読まない。
ここに集めておかないと、次の実装者は同じ種類の誤りを別の場所でまた作る。

**実例の出どころ:** 導入時点で載っている実例の PR 番号は、導入元テンプレート
([kant0123/ai-coding-template](https://github.com/kant0123/ai-coding-template))と、その導入先のものである。
誤りの種類は SpineBox にもそのまま当てはまるので残している。SpineBox で足す実例は SpineBox の PR 番号で書く。

**読むタイミング:** 着手時(`worktree-start` 手順 1)と push 前(`pr-finish` の前提の確認)。
push 前は、自分の差分が下の各種類に当てはまらないかを 1 つずつ確かめる。

**書くタイミング:** 差し戻しの指摘を妥当と判定して直したとき(`agy-review` 手順 3)。
既存の種類に当てはまれば実例を 1 行足し、無ければ種類を足す。
**未確認と判定した指摘は載せない。** 成立を確かめていないものを実装側の誤りとして記録すると、
推測が「繰り返される誤り」として次の実装者に読まれる。

## 書き方

- **単位は種類であって個々の指摘ではない。** 「`foo()` の空文字列を見ていなかった」ではなく
  「外部コマンドの出力が空・想定外の形のときを考えていない」と書く。事象ごとに書くと、
  次に別の関数で出る同じ誤りに当てはめられない。
- 各種類には「push 前に確かめること」を書く。自分の差分に対して答えられる問いの形にする。
- 実例は `PR 番号 — 場所 — 一行` で。修正コミットや PR を辿れれば詳細はそこにある(本文を貼らない)。
- 種類の数は増やしすぎない。似た種類が並んだら統合する。

誤検知(`false-positive`)と見逃し(`false-negative`)はここではなく上流の Issue に送る
(`review/README.md` の「記録の置き場所」)。未確認はこのリポジトリの Issue に起票する(上流には送らない。`agy-review` 手順 4)。ここはレビュー役ではなく**実装側の誤り**の記録。

> 初期の実例はこのテンプレート自身(`review/agy_review.py`)の開発で出たもの。
> 他プロジェクトに導入したら実例は消してよいが、種類はそのまま当てはまることが多い。

## 種類

### 外部コマンド・外部出力の異常系を考えていない

外部コマンド(`gh` / `git` / LLM CLI)やファイルシステムが返すものを、正常系の形のまま信じている。
空出力・非ゼロ終了・前置き付きの出力・エスケープされた値・OS で不正な文字を含む値で壊れる。

push 前に確かめること:

- 外部コマンドが失敗したとき・出力が空のとき、処理は止まるか。黙って成功扱いに倒れていないか
- 出力を解釈する正規表現・パーサは、引用符・空白・非 ASCII・前置き・CRLF の付いた値でも合うか
- 外部から来たパスを `resolve()` / `open()` する前に、不正な値で例外が出たときの扱いがあるか
- 同じ記録(PR コメント等)が何度も書かれうるとき、どれを正とするか(最新か・全部か)を決めているか
- 標準出力を解釈するとき、標準エラーを混ぜていないか(警告 1 行で値を読み違える)
- Windows PowerShell 5.1 のスクリプトで、`$ErrorActionPreference = "Stop"` のまま外部コマンドの stderr を受けていないか(警告・進み具合の 1 行で例外になる。成否は終了コードで見る)
- 同じ値を 2 か所で作って比べるとき、形(短縮 SHA の長さなど)がそろっているか

- PR #33 — `review/agy_review.py has_unverified_critical()` — 過去の評価も見ていて、記録し直しても差し止めが解けなかった

### 新しく足した分岐・関数にテストが無い

既存の純粋関数のテストはあるが、今回足した分岐(再試行・エラー経路・オプションの付与)には無い。
レビューで指摘されてから足すことが繰り返されている。

push 前に確かめること:

- 差分で足した `if` / `except` / 引数の付け足しのそれぞれに、そこを通るテストがあるか
- 外部プロセスを呼ぶ関数は、呼び出しをモックして「何を渡したか」を assert しているか

実例:

- PR #225 — `tests/test_mojibake.py` — `spinebox/mojibake.py` で新規追加した EUC-JP 誤読修復分岐や半角カナの安全性テストが欠落していた(agy レビューの WARNING。テストケースを追加)
- PR #8 — `review/agy_review.py` — `cmd_review` / `cmd_triage` / `cmd_check` / `call_agy` / `ci_state` にテストが無かった
- PR #23 — `review/agy_review.py call_agy()` — 再試行時の `--conversation` 付与にテストが無かった
- PR #61 — `spinebox/app.py background_metadata()` — 設定で有効にしたときに常駐する裏のスレッドにテストが無かった(既存の裏の解析は `tests/test_analysis.py` に有る。足したら同じ形で足す)
- PR #97 — `deploy/update_spinebox.ps1` — 「途中の手順が失敗しても起動し直す」「止められなければ何もしない」の分岐にテストが無かった(止める・起動するを `-TaskRunner` で差し替えられるようにしてテストを足した)
- PR #61 — `spinebox/app.py _run_metadata_fetch()` — 進み具合(`done`)を各作品の開始時にしか更新せず、全件完了後も `done < total` のままだった(完了時の状態を確かめるテストが無かった)
- PR #128 — `tests/test_deploy_scripts.py` — `worktree-cleanup.ps1` の削除テストで `.gitignore` 対象のファイルだけ置いて `.gitignore` 外の未追跡ファイルを置かず、削除後に `.git/worktrees/<id>` が消えてコミットを持つ作業ブランチに対する `git branch -D` が通ることも assert していなかった(agy レビューの WARNING)
- PR #262 — `spinebox/app.py get_page` — PDF のページを中身で `image/png` と見分ける分岐を足したのに、PNG を埋めた PDF で配信する経路のテストが無かった(agy レビューの WARNING。`make_png_pdf` で足した)

### ルールを足したのに、同じ流れを書いた他の箇所と食い違う

ルールを 1 か所(スキルの表・CLAUDE.md)に足し、同じ流れを別に書いている箇所
(手順の見出しと結び・フローチャート・他スキルのテンプレート・hook の判定)を直していない。
読む場所によって逆の指示が出る。機械で見張れるルールを文書にしか書かないのも同じ誤り。

push 前に確かめること:

- 足したルールのキーワードで `grep` して、同じ流れを書いた箇所(見出し・図・テンプレート)がすべて整合しているか
- そのルールは hook / CI で判定できる形か。できるなら判定を足したか

実例:

- PR #33 — `review/agy_review.py check_merge()` — 同じルールを hook が判定していなかった
- PR #33 — `.agent/skills/pr-finish/SKILL.md` — PR 本文テンプレートと手順 4 の振り分けに「未確認」が無かった
- PR #33 — `.agent/skills/agy-review/SKILL.md` フローチャート — 未確認の CRITICAL もマージに至る経路として描いていた(この種類を台帳に足した PR 自身で再発)
- PR #35 — `wiki/concepts/recurring-review-findings.md` — 「未確認は台帳に載せない」を足したが、同じページの送り先の説明に未確認の行き先が無かった
- PR #40 — `spinebox/duplicates.py candidate_counts()` — 画面の API は「一覧に見えている巻どうしの組」だけを出すのに、一覧の印の数は見える条件を掛けず、片方が missing になった候補を数えて「開いても何も出ない印」が残った(missing にして再現)

### 同じ規則で判定すべき対象を、種類ごとに先に別々に判定している

「同じ名前の巻はファイル数の多い方を残す」のように、対象全体を比べて決める規則を、対象の種類(単巻・CBZ 化する元)ごとに先に判定してから足し合わせる。
先に判定した側が結果(衝突など)を確定するので、あとからの全体の判定はそれらを対象から外し、種類をまたいだ比較が抜ける。

push 前に確かめること:

- 規則が比べる対象を全部列挙し、判定が 1 回の全体の比較になっているか(部分ごとの判定を先に走らせていないか)
- 種類が違う対象が同じ結果(同じ出力名)になるテストがあるか。片方の種類だけの重複を確かめたテストは、この漏れを通す

実例:

- PR #144 — `spinebox/organize/organizer.py _plan_range_cbz()` — 単巻の振り分け(`_classify_renames`)が単巻どうしの重複だけで衝突・譲りを決め、同じ名前の CBZ 化の元と比べなかった。単巻が同数で衝突していると、ファイル数の少ない元が `cbz` のまま確定した(単巻 5・5 と画像フォルダ 2 で再現し、`dedupe=False` で全体の判定へ寄せた)
- PR #249 — `spinebox/scanner.py archive_volume_specs()` — 目次・表紙の断片を「ほかに巻があるときだけ」除く判定を、画像のフォルダだけを並べた時点で行い、後から足す内側アーカイブを数えていなかった(断片と内側アーカイブだけのアーカイブで断片が巻に残る)。全部の巻の候補を並べた後に判定するよう移した(agy レビューの WARNING)
- PR #249 — `spinebox/scanner.py _is_fragment_folder()` — 「ほかに巻があるときだけ断片を外す」の「ほかの巻」に、断片どうしのフォルダと表紙 1 枚を数え、`Cover/` と `目次/` だけのフォルダで両方を外していた。アーカイブの中の判定(断片でない巻だけを数える)に揃えた(agy レビューの WARNING)

### 例外の規則で選ぶ範囲が、規則の前提より広い

既定の規則(しきい値・差)を外す例外を足すとき、例外で選んでよい対象(「同点の候補」など)を、既定の規則の判定に使っていた範囲(「差が足りない候補」)でそのまま絞ってしまう。
前提より広い対象から選ぶので、例外が本来の首位を押しのけて劣る候補を選ぶ。

push 前に確かめること:

- 例外が選べる対象は、例外の前提(同点・同種別など)を満たすものだけに絞っているか

### 名前の読み・統合の規則を、実データで見た形だけから広げる

本番データで見た名前(`チュートリアルが始まる前に 1 ボスキャラ…`・`週刊少年サンデー 2021年36号`・`フシノカミ ~副題`)に合わせて

(CLAUDE.md)ので、広い規則は誤読をそのまま作品・巻番号に昇格させる。

- 足した規則に当たる「作品名の一部」「別の作品」の例を 1 つ以上挙げ、テストで読まないことを確かめたか

- 同じ種類の別の表記(週刊の `N号` に対して月刊の `N月号`)まで規則が覆っているか

実例:

### 「手動の決定を守る」判定が、手動になりうる項目の全部を見ていない

「手で編集したものは外部ソース・自動処理で上書きしない」を、手動フラグを持つ項目の一部(作品名・巻の割り当て)でだけ判定している。

### 導出した行を、元(連携・設定)が消えても残す

「元から導出して入れる」処理が、入れる側だけを書いて、元が外れたとき(連携の解除・候補の変更・再取得で消えた候補)に入れた行を消す側を書いていない。
項目や巻の書誌では戻すのに、同じ導出で入れた別の表(別名)だけ残り、誤った手がかりが名寄せや統合に使われ続ける。

push 前に確かめること:

- 導出で書く表を全部列挙し、元が無くなったときにそれぞれが消える(または元の値へ戻る)か。表ごとに「入れる」と「外す」が対になっているか
- 外す処理は手動の行と、利用者が外した行(`dismissed_at`)を巻き込んでいないか
- 「連携を外した後」の状態を確かめるテストがあるか(入れる方のテストだけだと漏れる)

実例:

- PR #61 — `spinebox/linking.py _apply_aliases()` — 連携を外しても公開 DB 由来の別名が残り、誤った別名が後の名寄せの手がかりになりえた(項目と巻の書誌は外せていたが別名だけ漏れた)

### 再試行・再実行で前回の成果物を上書きする

### 件数が増える処理で、1 件ごとに全体を引き直している

「未処理を 1 件取って処理し、また未処理の一覧を引く」のように、ループの中で全件の SELECT や全件の `stat()` を繰り返す。
数件では気づかず、蔵書が増えると巻数の 2 乗で効く。

push 前に確かめること:

- ループの中で、全件を引く SQL・全件を対象にするファイルシステム操作を呼んでいないか。引き直しが要るのは「一巡して新しい対象が現れたとき」だけか
- 呼び出し回数をテストで数えたか(`pending()` の呼び出しを数えて件数に比例しないことを確かめるなど)
- 蔵書全体の巻をまとめて渡される関数が、巻ごとに SELECT を発行していないか(巻の行・書誌は IN で 500 件ずつまとめて引く。作品のように重複する対象は 1 回ずつ)。`set_trace_callback` で文の数が巻の数に比例しないことを確かめたか

実例:

- PR #40 — `spinebox/duplicates.py DuplicateScanner.run()` — 指紋を 1 巻作るたびに `pending()`(全巻の SELECT と作成済みの巻すべての `stat()`)を呼んでいた。`pending` の呼び出し回数を数えて再現し、1 巡ごとに直した
- PR #91 — `spinebox/organize/organizer.py name_values()` — 範囲指定が蔵書ルート全体の巻を渡すのに、巻ごとに 3 回 SELECT していた(20000 巻で 1.1 秒。10 万巻規模で効く)。文の数を数えるテストを足して `IN` でまとめて引くようにした
- PR #94 — `spinebox/stats.py collect()` — 全作品の表紙の有無を見るのに、作品ごとに `is_built()`(巻の行を 1 件 SELECT)を呼んでいた。`get_volume_rows()` で 500 件ずつ IN でまとめて引く `Thumbnails.are_built()` にし、文の数が巻の数に比例しないことを `set_trace_callback` で確かめるテストを足した
- PR #135 — `spinebox/organize/organizer.py _plan_range_cbz()` — `include_cbz` の計画で 1 巻 = 1 CBZ の巻ごとに `_classify_renames([r], ...)` を呼び、その中の `sources`・画像フォルダの SELECT が巻数ぶん出た。1 回の `_classify_renames` にまとめ、`folder_sources` / `source_paths` のキャッシュを渡すようにした。計画の SELECT 数が巻数に比例しないことを `set_trace_callback` で確かめるテストを足した
- PR #249 — `spinebox/works.py _settle_claims()` — 作品名を揃える段で、一覧の巻ごとに `work_volumes` を 1 件 SELECT していた(1 万巻で 2 万文)。割り当てを一度に引く辞書にし、文の数が巻の数に比例しないテストを足した(agy レビューの WARNING)
- #291 — `spinebox/app.py review_links()` — 確認待ちの作品ごとに `works.get_work()` を呼び、その中で全作品の項目と全巻を引き直していた(本番の 239 作品で 60 秒以上。レビューではなく利用者の報告で発覚)。`get_works()` でまとめて組み立て、文の数が作品の数に比例しないテストを足した。**一覧を返す API から「1 件の詳細を返す関数」を件数ぶん呼ばない**(その関数が全体を引いていないか中を見る)

### 共有すべき状態を、呼び出しごとに作るインスタンスに持たせている

レート制限の関門・接続プール・キャッシュのように、**リクエストをまたいで持ち越さないと意味がない状態**を、
リクエストごとに作るオブジェクトの中に持たせる。使うたびにリセットされて制限が効かず、逆に共有を渡すと
`close()` が呼び出し側のものまで閉じる(所有権が曖昧)。ドキュメントの使用例どおりに呼ぶと起きるので、テストでは
明示的に 1 つを渡していて気づけない。

push 前に確かめること:

- ドキュメント(wiki の使用例)どおりに「リクエストごとにインスタンスを作る」と、制限・接続は共有されるか。デフォルトの経路で確かめたか
- 外から渡されたオブジェクトを `close()` していないか。自分で作ったものだけを閉じているか

実例:

- PR #46 — `spinebox/metadata/service.py MetadataService` — 取得元ごとのレート制限の関門を持つ `HttpFetcher` を呼び出しごとに作り、`close()` は渡された共有 fetcher まで閉じていた。2 つのサービスの fetcher が別物になることと、渡した fetcher が閉じることをテストで再現して直した(プロセス共有の `shared_fetcher`、所有している fetcher だけを閉じる)

### 正規化の前提と、その前段の判定が別々の文字集合を見ている

文字列を種類(ローマ字 / 日本語)で振り分けてから正規化する処理で、振り分けの判定(`ord(c) < 128`)と、
振り分け先の正規化が扱う文字(マクロン付きラテン文字)が食い違う。正規化は対応しているのに、そこへ届かず日本語側に回り、

push 前に確かめること:

- 振り分ける関数と、振り分け先が扱う文字集合は一致しているか。境界の文字(マクロン・全角英数・記号だけの文字列)を入力にしたテストがあるか

### 利用者が打ったパスの綴りを、そのままデータベースの値と比べる

### 同じ根拠(evidence)を寄せる経路が複数あるとき、一方にだけ付けて他方で落とす

根拠の組み立て(`evidence` の文字列化・`parts` の付け足し)が、同じ入力に対する経路(早い return と遅い return、正規形と例外形)の

- 経路が分かれる手前で落とした分を、遅い経路で復元しているか。経路を要約する分岐ごとに、根拠の内容が変わっていないか

実例:

### シェルへ渡す文字列で、シェルのエスケープを考慮せず書いている

PowerShell の二重引用符の中では `` ` `` がエスケープ文字(`t → タブ、`a → BEL など)になる。Wiki・PR 本文のような自由文書を
そのまま二重引用符で渡すと、`code` のような組み込み記号が制御文字に化けて、文書が黙って壊れる。wiki-lint では拾えない。

push 前に確かめること:

- 自由文書をシェル経由で書くとき、デリミタ(単一/二重引用符・ファイル経由)のエスケープを考えたか
- 書いたファイルに制御文字(タブ・BEL)が入っていないかを、書いた後に機械で見たか

実例:

- PR #174 — `wiki/log.md` の備考 — PowerShell の二重引用符で渡した Python `-c` の文字列中の `` `trailing_number()` `` など 4 か所が、タブ・BEL 文字に化けてコミットされていた(agy レビューの NITPICK。機械で数えて修正)

### 一度取り出した値を捨てて、元の文字列から作り直す

構造化した結果(名前・著者・根拠の組)を途中まで作っておきながら、下流へは文字列だけ渡し、
渡された側で同じ文字列を再パースする。パースは前置き・括弧・番号を落とすので、2 回目では
元の情報が戻らず、項目が黙って空になる。

push 前に確かめること:

- パース結果を下流の関数へ渡すとき、その型のまま渡しているか。文字列へ戻して再パースしていないか
- 再パースで落ちる項目(著者・根拠・出所)が、テストで確かめられているか。値だけでなく
  `parts` のような根拠も見ているか

実例:

- PR #159 — `spinebox/works.py own_name()` — `_trailing_series()` が `parse_work_name()` の結果から
  `title` だけを渡し、`own_name()` がそれを再パースしていたため、`[著者] 作品名 01` の著者が落ちて
  作品の著者が空になった(著者つきの名前で再現し、`WorkName` をそのまま渡すように修正)

### 条件式で変数の意味を取り違え、境界を確かめていない

位置(`m.start()`)と値(`start`)を同じ条件で混用する。負のインデックスや先頭付近の参照で例外・誤判定になる。

push 前に確かめること:

- 条件式の各変数が「位置」か「値」か。位置を境界に使うとき、参照する添字の範囲を確かめたか
- 文字列の先頭・末尾付近を参照するとき、負のインデックスや `IndexError` にならないか
- 境界の入力(先頭の番号・末尾の数字・小数点)のテストがあるか

実例:

- PR #172 — `spinebox/naming.py:131 _find_number()` — 小数点の巻の判定で、巻番号の値 `start` を添字の境界として使い、`4.1巻` を `1巻` と誤読し、先頭付近で負のインデックスを参照しうる状態だった(agy レビューの WARNING。`m.start() >= 2` に修正し、`4.1巻` のテストを足した)
- PR #249 — `spinebox/naming.py _CHAPTER_LABEL` — `extra` の単語境界が `_` を単語の文字として扱うので `extra_01` に当たらなかった(さらに書き込み時のエスケープ誤りで `` が後退文字になっていた)。`(?![a-z])` にし、`extra_01` `Extra-02` `Extraordinary` のテストを足した(agy レビューの WARNING)
- PR #249 — `spinebox/naming.py is_fragment_name()` / `_RULES` の ch.N — 1 文字の名前を一律に断片とし漢字 1 文字の作品名(`岳`)を落とした。`c(?=\d)` を IGNORECASE の中に置き `C100`(コミックマーケットの回)を話 100 と読んだ。漢字・かなを除き、`(?-i:c)` にした(agy レビューの WARNING)

### 共通の後処理を分岐の片側だけに置いている

`if` の片側でだけ行う処理を、両方の分岐に必要な共通の後処理なのに片側に置く。もう一方の分岐ではその処理が抜ける。

push 前に確かめること:

- `if` / `else` の両方に同じ後処理が必要か。必要なら分岐の外(後ろ)に置いたか
- 両方の分岐を通るテストがあるか。片側だけのテストは漏れを通す

実例:

- PR #172 — `spinebox/works.py:938 _assign_volumes()` — 番号付きの作品から系列名の作品へ付け替えるときの `_merge_links()` を、系列名の作品を新設する `if target is None:` の側にだけ置き、既存の系列名の作品へ付け替える `else` 側では連携が移らなかった(agy レビューの WARNING。分岐の外へ移し、2 巻目以降の連携を移すテストを足した)

### 解析規則を変えたのに、既存データを読み直す版を上げていない

`parse_number()` などの読み方を変えたとき、`SCAN_VERSION` を上げないと、同じサイズ・mtime のアーカイブは unchanged と判定され、既存 DB の番号が読み直されない。

push 前に確かめること:

- 名前・番号の読み方を変えたか。変えたなら `SCAN_VERSION` を上げたか
- 既存 DB を読み直すテスト、または版を上げたことのテストがあるか
- 名寄せで直る導出値と、スキャンでしか直らない値(`number_*`)を区別しているか

実例:

- PR #225 — `spinebox/scanner.py:58 SCAN_VERSION` — タイトル生成と巻番号抽出に文字化け修復(`fix_mojibake`)を適用したのに `SCAN_VERSION` を 7 のままにしていた(agy レビューの WARNING。8 に上げた)
- PR #172 — `spinebox/scanner.py:58 SCAN_VERSION` — `parse_number()` に `卷` と小数点の巻の読み方を足したのに `SCAN_VERSION` を 2 のままにしていた(agy レビューの WARNING。3 に上げた)

### 変化が無ければ書かない処理で、条件の抜けにより毎回書く

「冪等で、変化が無ければ書かない」処理の更新条件に、対象の値が存在するかのガードを入れず、値が無い行にも毎回 UPDATE を発行する。`updated_at` が毎回変わり、契約と DB の書き込み量が破れる。

push 前に確かめること:

- 更新する条件は、対象の値が NULL の行を除外しているか
- 何も変えない再実行で、行の `updated_at` が変わらないテストがあるか
- ループ内で、条件が常に真になる行がないか

実例:

- PR #172 — `spinebox/works.py:918 _apply_trailing_numbers()` — 小数点の巻の番号を消す条件に `parse_number() is None` だけを入れ、`number_kind is None` の巻も毎回 UPDATE して `updated_at` を書き換えていた(agy レビューの WARNING。`number_kind is not None` のガードを足し、番号なしの巻の行が変わらないテストを足した)

### 前提条件の内側に置いた処理が、前提を満たさない自然な状態で実行されない

「A なら B を直す」処理を、A を満たす分岐の内側に置く。A は B の結果で満たされることがあるため、自然な入力では B が一度も走らず、機能がデッドコードになる。テストが A を事前に作っていると、この循環を隠す。

push 前に確かめること:

- 処理の前提(A)が、その処理の結果で初めて満たされるか。なら処理を前提の判定より前に置いたか
- 自然な入力(別名・公開 DB の連携が無い状態)で処理が走るテストがあるか
- 前提を満たさないとき、別の作品を新設して元の作品が孤立しないか

実例:

- PR #172 — `spinebox/works.py _assign_volumes()` — `_refresh_title()` を `norm in work.names` の分岐の内側に置いていた。小数点の巻を誤読した 1 巻作品は系列名の別名を持たないのが自然なので、`norm in work.names` が偽になり、作品名が直らず、新しい系列作品を作って元の作品が孤立した(agy レビューの WARNING。判定の前に呼ぶよう移し、テストから事前の `add_alias` を外した)

### 撤回(revert)や一括削除で、維持すべき機能・ログ・テストを巻き添えで消す

過去の PR の変更を撤回するとき、機械的な `git revert` や差分の一括削除をそのまま適用し、その PR より後に追記された時系列ログ(`wiki/log.md`)や、同じ PR に含まれていたが撤回対象ではない機能・ドキュメント記述・テストのアサーションまで一緒に消してしまう。追記専用ログの履歴が失われ、維持すべき機能のドキュメントと実装が乖離し、テストの検証が弱まる。

push 前に確かめること:

- `git revert` や削除を行う際、追記専用のファイル(`wiki/log.md`)の過去ログや後続 PR のエントリを上書き・削除していないか。revert も末尾に新しく追記しているか
- 文字列置換(スクリプトの `str.replace()` やエディタの全置換)を行う際、追記専用ファイル(`wiki/log.md`)の過去ログや無関係な行まで巻き込んで置換していないか(1 箇所のみ置換するか、末尾に追記する形にしているか)
- 撤回する対象の機能以外の機能(同時に追加・修正されたが維持するもの)の記述・コード・テストを一緒に消していないか
- `git diff` で削除された行を 1 行ずつ確認し、撤回対象外のキーワードが含まれていないか

実例:

- PR #213 — `wiki/log.md` / `wiki/components/backend.md` / `wiki/concepts/work-search.md` / `frontend/src/works/Works.test.tsx` — PR #191 の revert で `wiki/log.md` の後続 PR #197・#201 のエントリが巻き添えで削除され、維持する `read_later` フィルタの API 契約表・検索仕様の記述、およびフロントのテストのアサーションまで削除されていた(agy レビューの WARNING 2 件・NITPICK 1 件。復元して修正)
- PR #216 — `wiki/log.md` — スクリプトによる文字列の一括置換(`replace`)で、最新エントリだけでなく過去の PR (#159, #160, #164, #174, #172) の更新行まで同じ文字列として置換され、同一ページへの重複リンクが混入していた(agy レビューの WARNING。過去ログを元に戻し最新エントリのみ追記する形に修正)
- PR #302 — `wiki/log.md` — 最新エントリの「更新:」行を `sed` で書き換えたとき、同じ文面の過去の行(PR #192・#201)にも当たって履歴が変わった(agy レビューの NITPICK。置換後に `git diff` で当たった行を数える)

### 文字化け修復の判定で、正常な別文字コードの文字列が偶然デコードされる誤爆を考えていない

文字コードの誤読を再デコードで修復する際、対象エンコーディングのバイト範囲が重なる別の正常な文字列(例: CP932 の半角カナ 2 文字が EUC-JP の第 1 水準漢字 1 文字とバイト値が完全一致する)が偶然エラーなくデコードできてしまうことを考慮せず、緩い条件(漢字 2 文字以上など)だけで修復成功と判定している。正常な半角カナや第 2 水準漢字を含むタイトルが別の無関係な漢字に不可逆的に置換される。

push 前に確かめること:

- 再デコードが成功するバイト範囲に、意図しない正常な文字列(半角カナ、アクセント付き欧文文字、第 2 水準漢字など)が含まれうるか
- 元の文字列の特徴(半角カナの連続など)と、復元後の文字列の特徴(全角ひらがな・カタカナを含むかなど)の両面でガードしているか
- 正常な半角カナの連続(ｱｲｳｴ など)や欧文単語を入力にした安全性のテストがあるか
- 新しい場所で再デコードを足すとき、この節の実例(`élégant` `château` `ｱｲｳｴ`)をそのままテストに入れたか

実例:

- PR #259 — `spinebox/archive/rar4.py recovered_name()` — RAR4 の OEM 名を cp932 で読み直す判定を「日本語 2 文字以上」だけにしたため、西欧の Windows で作った rar の OEM 名(cp1252)の `élégant` が `駘馮ant` に誤変換されていた(同じ台帳の #225 と同じ機序を別の場所で再発。agy レビューの CRITICAL。Unicode 名が OEM 名の DOS 読み(cp437 / cp850)そのものであること・英字と漢字かなが隣り合わないことの二重ガードに修正)
- PR #225 — `spinebox/mojibake.py:59 fix_mojibake()` — EUC-JP 誤読修復判定で `len(_JAPANESE.findall(fixed)) >= 2` だけで成功としていたため、正常な半角カナ `ｱｲｳｴ`(4文字)が EUC-JP の漢字 `塊慨` に誤変換されていた(agy レビューの CRITICAL。元テキストの半角カナ連続と復元後の全角かな必須の二重ガードに修正)
- PR #225 — `spinebox/mojibake.py:59 fix_mojibake()` — 欧文コードページ誤読修復判定で `kanji_count >= 2` を無条件で許容していたため、小文字アクセント付き母音を複数含む欧文単語 `élégant`・`téléphone`・`céréale` 等が Latin-1 経由で Shift_JIS 第 2 水準漢字のバイト列と偶然一致して `齔齠ant` 等に誤変換されていた(agy レビューの CRITICAL。テキストが欧文文字・記号のみで構成される場合は全角かな必須とするガードに修正)
- PR #225 — `spinebox/mojibake.py:59 fix_mojibake()` — 欧文コードページ誤読修復判定で、テキストが欧文文字のみ(`is_western`)の場合でも全角かな 1 文字で無条件に修復判定していたため、フランス語単語に含まれる `â`(CP437 で 0x83)の直後に ASCII 小文字が続く単語 `château`・`gâteau`・`grâce` 等が、Shift_JIS のカタカナ 1 文字(0x83 0x74='フ', 0x83 0x63='ツ' 等)を含む文字列 `chフeau`・`grツe` 等に不可逆的に誤変換されていた(agy レビューの CRITICAL。`is_western` の場合は連続した全角かな 2 文字以上を必須とするガードに修正)
- PR #225 — `spinebox/mojibake.py:59 fix_mojibake()` — EUC-JP 誤読修復判定で半角カナ 2 文字以上(`[｡-ﾟ]{2,}`)かつ全角かな 1 文字としていたため、正常な半角カナ 2 文字単語 `ｴｱ`・`ｵﾝ` 等が EUC-JP の全角かな 1 文字 `か`・`ヱ` に誤変換されていた(agy レビューの CRITICAL。元テキストに半角カナ 4 文字以上の連続を含み、かつ復元後に全角かな 2 文字以上および非 ASCII 文字 2 文字以上を必須とするガードに修正)
- PR #225 — `spinebox/mojibake.py:59 fix_mojibake()` — `château de grâce` のように複数単語に `â` を含むタイトルで散発したカタカナが計 2 文字となりガードをすり抜ける問題、および商標記号 `™`(`℀-⅏`)が `_WESTERN_TEXT` から漏れて誤変換される問題(agy レビューの CRITICAL。`has_kana_seq` による連続全角かな必須化と正規表現拡張で修正)

### 新しい画面・モックが、同じ種類の既存の画面とバックエンドの規約から外れる

検索欄などを足すとき、同じ種類の既存の画面(作品一覧の検索)の書き方・設計方針(`wiki/components/frontend.md`)と、
バックエンドの規則(正規化)を確かめずに書く。placeholder で説明する、境界色のトークンが違う、モック API だけ単純な部分一致になる、など。

push 前に確かめること:

- 同じ種類の入力・表示が既にあるなら、その実装(`Works.tsx` の検索欄など)と Wiki の方針(入力欄に placeholder を使わず、サポートテキストと `aria-describedby` で示す)に揃えているか
- バックエンドが正規化して比べる項目を、モック API でも同じ関数(`normalizeSearch`)で比べているか。モックだけ通って実機で結果が違う状態になっていないか
- テストが、足した対象(著者・別名など)のそれぞれに当たる入力を持っているか(名前だけで当てて通していないか)

実例:

- PR #230 — `frontend/src/works/WorkProposals.tsx` / `frontend/src/mock/mockWorks.ts` / `tests/test_linking.py` — 統合の提案の絞り込みで、placeholder での説明・モックの単純な `toLowerCase()` 比較・著者と別名が空のテストを、agy レビューで指摘された

### 規約に「上の」「下の」と相対的に書き、参照先を取り違えさせる・手順名を実際の手順とずらす

CLAUDE.md のように長い文書へ規則を足すとき、「上のワークフロー」と書くと実際の定義は下の節にあり、点検が前方だけで終わる。
また「prune」のように、実際の後始末手順(`scripts/worktree-cleanup.ps1`)と違う操作名で書くと、別のコマンドで代用される。

push 前に確かめること:

- 規約文中の参照先を「上・下」でなく節名・固有名で指しているか
- 手順や操作の名前が、既存スキル・スクリプトの実際の名前と一致しているか(代用してはいけない操作はその旨を書く)

実例:

- PR #237 — `CLAUDE.md` のラップアップ報告 — 「上のワークフロー」と「worktree は prune 済みか」を、agy レビューで指摘された

### 結果に含めない対象を、短絡評価の既定値で含めてしまう

「見つからない・見えない対象は結果に含めない」オプションがあるのに、対象の有無を `row is not None and ...` の短絡評価で確かめ、例外の経路(除外)を通さずに既定の False を結果へ入れてしまう。キーの有無で件数を数える呼び出し側では、除外したはずの対象が数えられる。

push 前に確かめること:

- 「結果に含めない」オプションがある関数で、対象が無い・読めない場合がすべて同じ経路(例外・`continue`)を通るか
- 存在しない ID・行が無い ID を渡したテストが、オプションの両方にあるか

実例:

- PR #303 — `spinebox/thumbs.py:181 are_built()` — `row is not None and self.store.contains(...)` が `row is None` のとき `_key()` の例外を飛ばし、`include_unavailable=False` でも `{vid: False}` を返した(存在しない id で再現し、`raise VolumeNotFound(vid)` に修正)
